A slow query, indexes and EXPLAIN

A query that searches a column without an index must read every row of the table. On a small table nobody notices. On a table of a million rows it takes seconds, every time.

Put EXPLAIN in front of the query to see how the server will run it.

EXPLAIN SELECT * FROM orders WHERE status = 'new';

Read the type and key columns. type ALL with key NULL means a full table scan. The rows column is the server's estimate of how many rows it will read.

Add an index on the column being searched.

CREATE INDEX idx_orders_status ON orders (status);

Run EXPLAIN again. Usually key now names the index and type is ref, so the server goes straight to the matching rows. If most rows have the value searched for, it may still read the whole table, because that is faster.

Index what the queries use. Columns in WHERE, in JOIN conditions and in ORDER BY are the candidates. For a query that filters on two columns, one index on both in that order, (customer_id, created_at), serves WHERE customer_id = ? ORDER BY created_at and also queries on customer_id alone, but not on created_at alone.

What defeats an index. A function around the column, WHERE YEAR(created_at) = 2026, cannot use an index on created_at. Write a range instead, WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'. LIKE '%word' cannot use one either.

Indexes are not free. Each one takes disk space and slows every insert and update a little, so do not index every column. SHOW INDEX FROM orders; lists the ones a table has.

Creating an index on a big table takes time and work from the server. Do it when the site is quiet, with a backup.
